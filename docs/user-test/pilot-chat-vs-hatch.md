# 파일럿: 채팅 vs Hatch (2026-11-03, #121)

사람 테스트(과제 8) 전에 **측정 방법이 쓸 만한지** 보려고, 같은 아이디어를 같은 모델로 두 방식에 한 번씩 돌렸다.
사람이 아니라 기계가 돌린 1회 측정이다. 사용자 가치의 증거가 아니라 과제 8에서 볼 숫자의 첫 값이다.

## 조건
- 아이디어 · 맥락: 대본의 예시 "동네 헬스장 PT 예약 앱" + 목표 고객 · 목표 지표 두 칸
- 모델: 둘 다 `claude-opus-5-5`, `claude -p`, 도구 끔, 전역 설정 안 섞음
- **채팅**: 단계마다 새 대화에 앞 문서를 통째로 붙여 넣고 "기획안 / 개발 로드맵 / PRD를 마크다운으로 써 줘". 채팅으로 할 수 있는 가장 좋은 경우
- **Hatch**: main(`4d9a403`)을 임시 데이터 폴더로 띄우고 화면에서 버튼으로 기획안 → 확인 질문 → 로드맵 → PRD
- 세기: `tools/count-claims.mjs` (숫자+단위, `[확인 필요]` 안은 뺌). 무작위 30개를 사람이 읽어 거짓 양성(목록 번호)을 찾고 규칙을 고친 뒤 다시 셈

## 결과

| 항목 | 채팅 | Hatch |
| --- | --- | --- |
| 세 문서 생성 시간 | 244초 (78 · 70 · 96) | 89초 (22 · 30 · 37), 확인 질문 19초 따로 |
| 세 문서 글자 수 | 26,985 | 8,216 |
| 근거 없이 단정한 수치 | 217개 | 0개 (센 1개는 질문 문장 속 "1건") |
| `[확인 필요]`로 남긴 곳 | 0곳 | 58곳 |
| PRD에 새로 생긴 수치 (앞 문서에 없던 것) | 4개 (5건, 5회, 1분, 0회) | 0개 |
| 물어볼 질문 목록 | 없음 | 11개 (고객 2 · 기획 담당 9) |
| 기획안을 고친 뒤 표시 | 없음 | 로드맵에만 "앞 문서가 바뀜". **PRD는 "완료" 그대로** |
| 정가 기준 비용 | $0.78 (3회 호출) | $0.43 (4회 호출) |

채팅의 단정 수치 무작위 30개(규칙 고치기 전) 판독: 목록 번호 6개(규칙에서 뺌), 나머지 24개는 입력에 없던 수치
- 제품 규칙 · 가격 10개 (예: 월 29,000원부터, 잔여 3회 알림, 대체 시간 3개 제안). 이 중 1개만 질문 형태
- 일정 8개 (파일럿 8–11주, 12주에 판단)
- 목표 3개 (주간 예약 메시지 70% 감소, 첫 시작 5분 이내)
- 사실 가정 3개 (트레이너 3~5명 헬스장, 주 2회 PT)

## 읽는 법 · 한계
- 시간 차이는 대부분 **글 길이** 차이다. 같은 모델이고, Hatch 프롬프트가 짧게 쓰고 모르면 비워 두게 한다
- 채팅에 "모르는 건 [확인 필요]로 남겨"라고 부탁하면 차이는 줄 것이다. 사람이 매번 그 부탁을 하는지가 과제 8에서 볼 것
- 1회 측정이다. 같은 조건을 다시 돌리면 숫자가 달라진다
- 단정 수치 = 근거가 없는 것이지 틀린 것은 아니다. 목표 · 일정 · 가격은 PO가 정할 결정이다
- Hatch의 낡음 표시가 바로 다음 문서에만 붙는다(가설 H4)는 것을 파일럿에서 다시 확인했다 → #61
