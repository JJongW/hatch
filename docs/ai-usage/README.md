Hatch는 하루(2026-10-28) 동안 Claude Code로 만들었다. 사람(PO)은 무엇을 · 왜를 정하고 승인했고, AI는 설계 초안 · 구현 · 리뷰 · 검증을 맡았다.

## 1. 쓴 도구
- **Claude Code** (데스크톱 앱 Code 탭, 모델 Opus) — 설계 · 구현 · 리뷰 · Git · GitHub 작업 전부
- **서브에이전트** — 작업 하나당 새 에이전트(구현 → 리뷰 → 수정). 컨텍스트를 나눠 쓰려고
- **병렬 세션** — 독립 작업(C-2 · C-3 · C-4)은 세션을 따로 띄워 동시에 진행
- **앱 안 생성은 로컬 `claude -p`** — API 키 없이 내 Claude 구독으로 문서를 만든다 ([결정](../decisions/2026-10-28_로컬-claude-생성.md))
- **브라우저 패널** — dev 서버 화면을 AI가 직접 눌러 보고 콘솔 오류 확인

## 2. 작업 흐름 — 사람이 정하고 AI가 만든다
```
설계(spec) → 계획(plan) → 이슈 → 브랜치 → 구현(서브에이전트) → 리뷰(hatch-reviewer) → 검증 → PR → 내 승인 → squash 머지
```
- 단계를 A(아이디어 뱅크) · B(문서 체인) · C(PO 도구) · D(디자인)로 나눴다. 단계마다 AI가 질문 → 내가 고름 → spec → 내가 "확정" → plan
- **내가 멈춰서 승인하는 지점**: 설계 확정, 머지, 파일 삭제, force push, 전역 설정 변경. 나머지는 AI가 "짧게 설명 → 진행"
- 결정 기록: AI에게 고를 질문은 객관식으로 받았다 (예: C단계 "결과 저장 방식", "입력 문서", "협상 방식", "VOC 입력"). 고른 답은 spec §1 "결정"에 날짜와 함께 남겼다
- 검증 명령은 하나로 고정: `npm run lint && npm run typecheck && npm test && npm run build`. "됐다"고 말하기 전에 실제로 돌리고, 안 돌린 건 안 돌렸다고 쓰게 했다

## 3. CLAUDE.md — 폴더마다 짧게
AI가 필요한 문서만 읽게 하려고 CLAUDE.md를 폴더마다 나눴다 ([결정](../decisions/2026-10-28_폴더별-CLAUDE-md.md)).

| 파일 | 줄 수 | 역할 |
| --- | --- | --- |
| `CLAUDE.md` (루트) | 45 | 지금 단계 · 폴더 지도 · 작업 흐름 · 검증 명령 · 공통 규칙 |
| `docs/CLAUDE.md` | ~30 | 이슈 · 브랜치 · 커밋 · PR · 머지 규칙 · why 기록 규칙 |
| `src/app/` · `src/app/tools/` · `src/components/` | 17~25 | 화면 규칙 · import 규칙 |
| `src/lib/storage/` · `claude/` · `chain/` · `prompts/` · `tools/` | 12~26 | 영역별 파일 지도 · 규칙 · 갈아탈 신호 · 하지 말 것 |
| `bridge/` | 26 | 보류 표시 |

- 규칙: **루트 60줄, 폴더 30줄 이하.** 넘으면 `docs/`로 빼고 링크만
- 폴더 CLAUDE.md는 같은 칸을 쓴다: 파일 지도 · 규칙 · 갈아탈 신호 · 하지 말 것
- 루트 "폴더 지도" 표가 폴더 → 담당 에이전트를 이어 준다. AI는 루트 → 일할 폴더 CLAUDE.md 순서로만 읽는다
- 일하면서 배운 것은 바로 그 폴더 CLAUDE.md에 넣었다 (예: `instant = false`, 새 도구 테스트 위치)

## 4. 에이전트 · 스킬 (`.claude/`)
| 이름 | 종류 | 언제 |
| --- | --- | --- |
| `ui-builder` | 에이전트 | 화면 · 저장 (A) |
| `chain-author` | 에이전트 | 문서 체인 · 프롬프트 (B) |
| `tool-builder` | 에이전트 | PO 도구 (C). C-2~4를 병렬로 만든 주체 |
| `hatch-reviewer` | 에이전트(읽기 전용) | PR 전 검사. 🔴 · 🟡로 지적 |
| `bridge-engineer` | 에이전트 | 맥 중계 서버 — 보류 |
| `montage-ui` | 스킬 | Montage 컴포넌트 쓰는 법 · TDS는 참고만 |
| `chain-step` | 스킬 | 체인 단계 하나 추가 절차 |
| `new-po-tool` | 스킬 | PO 도구 하나 추가 8단계 — C-1에서 실제로 만들어 보고 고친 절차 |

- **스킬은 "같은 절차를 손으로 3번 넘게 하면 만든다"** 규칙으로 만들었다
- `new-po-tool` 스킬이 핵심이다. C-1에서 틀과 첫 도구(PRD 리뷰)를 만든 뒤, 실제로 겪은 함정(영어 zod 메시지, React 19 폼 리셋)을 스킬에 넣었다. 그다음 C-2~4 세 세션이 **이 스킬과 폴더 CLAUDE.md만 보고** 동시에 도구를 만들었고, 세 PR 모두 공통 틀을 건드리지 않고 지적 0~4건으로 끝났다
- 외부 스킬: superpowers(brainstorming → writing-plans → subagent-driven-development), why(변경 이유 기록)

## 5. 토큰 관리
| 방법 | 효과 |
| --- | --- |
| 폴더별 CLAUDE.md · 줄 수 상한 | 일할 폴더 문서(30줄 이하)만 읽는다. 전체 문서를 매번 읽지 않는다 |
| 서브에이전트에 일을 나눔 | 구현 · 리뷰 기록이 메인 대화에 쌓이지 않는다. 메인은 결과 한 줄만 받는다 |
| 일은 파일로 넘김 | 계획에서 해당 Task만 뽑은 brief 파일, diff를 묶은 review package 파일, 보고서 파일. 대화에 diff를 붙이지 않는다 |
| 모델을 일에 맞춤 | 계획 그대로 옮기는 구현은 가벼운 모델, 판단이 필요한 구현 · 재리뷰는 중간(Sonnet), 브랜치 전체 최종 리뷰만 가장 강한 모델(Opus) |
| 진행 장부(ledger) | 대화가 길어져 요약(compaction)돼도 장부의 "Task N: complete"를 보고 이어 간다. 끝난 작업을 다시 시키는 낭비를 막는다 |
| 병렬 세션 | C-2~4를 각자 세션에서 — 한 대화에 세 도구 맥락이 섞이지 않는다 |
| 프롬프트 · AI 출력 구조화 | 프롬프트는 `src/lib/prompts/`에만. AI 출력은 JSON 스키마로 받아 형식 오류 재시도가 없다 |

실제 수치(C-1 마무리): 브랜치 전체 리뷰 약 13.9만 토큰, 수정 약 11.8만, 재리뷰 약 8.8만. 재리뷰는 바뀐 부분 diff만 줘서 전체 리뷰의 2/3 수준으로 끝났다.

## 6. AI 실수를 잡는 장치
- **작업마다 리뷰** — 구현한 에이전트가 아닌 다른 에이전트가 spec 대비 · 품질을 본다. 작은 지적은 장부에 "→ 최종"으로 미뤘다가 최종 리뷰에서 정리
- **실제 실행** — 단위 테스트(가짜 claude)만 믿지 않고 단계 끝마다 실제 `claude`로 한 번 돌려 결과 파일과 화면을 본다. 조사 오류 · MVP 중복은 여기서만 잡혔다
- **사람 승인 지점** — 머지 · 삭제 · force push는 AI가 혼자 못 한다. 병렬 PR 충돌 때 AI가 force push 대신 merge로 돌아간 것도 이 규칙 때문
- 사례 13건: [mistakes.md](mistakes.md)
