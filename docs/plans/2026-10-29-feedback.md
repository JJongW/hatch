# 외부 피드백 반영 계획

**날짜**: 2026-10-29 · **상태**: 1단계 진행 중

## 받은 피드백 (요약 · 원문 순서)
1. PM/PO의 핵심은 문서 작성이 아니다. 풀 가치가 있는 문제를 찾고, 고객 · 사업 근거로 우선순위를 정하고, 팀이 같은 결정을 이해하게 돕고, 출시 후 결과를 보고 다시 판단하는 일이다. AI는 조사 정리 · 초안 · 반론 탐색 · 변경 추적을 돕지만 고객 근거와 책임 있는 결정을 대신하지 못한다.
2. "Claude로 문서를 만들어 준다"에서 끝나면 차별점이 약하다. 프로젝트 맥락을 한 번 입력해 여러 작업에서 재사용하고, 결정 이유와 불확실성을 남기고, 문서 변경이 다른 문서에 미치는 영향을 보여 줘야 Claude 채팅보다 나은 이유가 된다.
3. 좋은 기반: 한 줄 아이디어로 시작, PRD 리뷰의 직군별 반론과 재리뷰 변화, `[확인 필요]`, 이전 문서 변경 경고. 변경 경고는 "무엇이 왜 바뀌었고 어디에 영향이 있는지"까지 발전시킬 만하다.
4. 가장 먼저 고칠 UX는 상세 화면. 수정 입력창이 먼저 크게 보여 현재 상태와 다음 행동이 묻힌다. 제목 · 메모는 읽기 화면, 필요할 때만 수정. 위에는 "해결하려는 문제 → 확인된 근거와 모르는 것 → 지금 내려야 할 결정 → 추천 다음 행동". 문서는 탭 · 목차로 열어 이중 스크롤을 줄인다.
5. 도구 화면은 입력 우선순위를 실제 작업에 맞춘다. VOC는 고객 의견을 맨 위에, 제품 맥락은 프로젝트에서 가져오거나 선택적으로. 협상은 첫 라운드 후에 "내 답"을 받는다.
6. 데모에서 가능한 행동과 불가능한 행동이 분명해야 한다. 저장 · 실행 버튼이 실제 버튼처럼 보여 혼란스럽다. "예시 입력 불러오기 → 샘플 결과 보기"를 연결하고, 못 쓰는 곳은 "내 환경에서 사용하기"로 안내. 배너의 GitHub README가 공개 접근에서 404.
7. 새 도구보다 세 가지 연결: 프로젝트 기본 맥락과 결정 · 보류 이유 저장, `[확인 필요]`를 고객 질문 · 담당자 확인 항목으로, 변경 비교 후 사람이 승인해야 다른 문서에 반영. 실사용판에는 Mac mini/Claude 연결 상태, 실패 이유, 재시도 · 취소, 결과 보존.
8. 뒤로 미뤄도 되는 것: 6종 문서를 정해진 순서로 만드는 흐름, 전면의 AI 점수, 협상 점수. VOC의 "건수 × 심각도"는 출발점으로만, 고객군 · 제품 목표 · 해결 비용을 함께 보고 사람이 우선순위를 정한다.

## 방향 (요구사항 다시 쓰기)
- Hatch의 가치 = **맥락을 한 번 넣으면 여러 작업에 재사용** · **결정 이유와 모르는 것을 남김** · **문서 변경의 영향을 보여 줌**
- 우선순위와 결정은 사람이 한다. AI는 정리 · 초안 · 반론 · 변경 추적까지
- 처음 쓰는 사람이 멈칫하는 곳부터 고친다

미루는 것: 정해진 순서로 6문서를 다 채우는 흐름(없애진 않고 "필요한 문서만" 쪽으로), 새 도구 추가.

## 위험
- 높음 · 일정: 4단계는 저장 구조 · 프롬프트 · 화면이 같이 바뀐다. 제출 전엔 4a 또는 4c 하나를 권한다
- 중간 · 데모: 데모는 생성을 못 하므로 새 기능마다 샘플 결과를 `demo-data/`에 넣어야 보여 줄 수 있다
- 중간 · 공개: README 404는 저장소가 비공개라서다. 공개하려면 커밋 이력 전체의 비밀값 · 개인정보 검사가 먼저다 (사용자 결정 대기)
- 낮음 · 저장 형식: 기존 md와 호환은 storage 테스트로 지킨다

## 진행 방식
항목마다 이슈 → 브랜치 → PR → why 기록 → 승인 후 머지. 4단계는 설계 → spec → plan 뒤 구현.
